# 软件架构拓扑图：阅读指南 (Reading Guide)

此文档旨在帮助开发者深入理解 `docs/software_topology.mmd` 拓扑图，将其作为系统健康监测与性能优化的“作战地图”。

## 1. 颜色编码：战场压力 (Color Code)
我们使用**红绿灯**逻辑来标注任务的繁忙程度与优化紧迫性：

*   🔴 **红色区块 (High Priority/Load)**
    *   **含义**: 系统最繁忙、压力最大的任务。
    *   **典型示例**: `audio_input` (43%), `audio_detection` (15%)。
    *   **关注点**: 这些是系统的“心脏”。如果它们变红，说明它们在全力工作。这是**重点监控对象**，任何阻塞都可能导致功能失效（如音频卡顿）。
*   🟡 **黄色区块 (Medium Priority)**
    *   **含义**: 负载中等，或优先级较低但计算量大的任务。
    *   **典型示例**: `imu_ai_task` (16%)。
    *   **关注点**: **优化潜力最大的区域**。例如，优化前的 IMU 任务曾是红色（33%），通过降频和调度优化变成了黄色（16%），释放了宝贵算力。
*   🟢 **绿色区块 (Low Priority/Idle)**
    *   **含义**: 轻松的任务，大部分时间在通过 `vTaskDelay` 或 `xQueueReceive` 等待事件。
    *   **典型示例**: `main` (<1%)。
    *   **关注点**: 系统的业务指挥官，应该一直保持冷静（绿色），只处理状态流转和逻辑决策。
*   🟣 **紫色区块 (System)**
    *   **含义**: `Wifi`, `LwIP`, `EspTimer` 等操作系统内核级或驱动级任务。
    *   **关注点**: 只要不出现丢包或看门狗超时，通常无需干预。

## 2. 数据解读：身份铭牌 (Data Interpretation)
每个方块代表一个 **FreeRTOS 任务 (Task)**，其中包含三个关键指标：

> **示例**:
> **audio_input**
> **Prio:8**
> **CPU:43%**

*   **Prio (优先级)**: 决定谁说了算。
    *   数字越大，权利越大。
    *   阶层示例: `Prio:23` (Wifi) > `Prio:8` (录音) > `Prio:1` (业务)。
    *   **潜规则**: 高优先级任务可以随时打断低优先级任务。
*   **CPU (占用率)**: 任务消耗的时间片占比。
    *   **数据来源**: 通过 `vTaskGetRunTimeStats()` 从内核抓取的真实数据。
    *   **深度原理 (How it works)**:
        1.  **高精度计时器**: FreeRTOS 使用一个比系统 tick 快 10-20 倍的硬件定时器。
        2.  **打卡机制**: 任务切入时记录 $T_{in}$，切出时记录 $T_{out}$，差值累加到该任务的总运行时间里。
        3.  **公式**: $\text{CPU\%} = \frac{\text{任务累计运行时间}}{\text{系统总运行时间}} \times 100\%$
    *   **举例**: 
        > 假设系统运行了 100秒 (Total)。
        > `audio_input` 任务每次处理音频耗时很短，但频率很高，前前后后累计运行了 43秒。
        > 那么它的占用率就是 **43%**。
        > 剩下的 57秒 里，大部分时间 CPU 都在运行 `IDLE` (空闲) 任务。

## 3. 图形符号 (Shapes & Symbols)
*   🟦 **矩形 (Rectangle)**: **软件任务 (Software Task)**。在 FreeRTOS 中实际运行的线程。
*   🟡 **圆形/六边形 (Circle/Hexagon)**: **物理硬件 (Hardware)**。如麦克风、扬声器、屏幕、传感器。
*   🏁 **虚线框 (Dashed Subgraph)**: **逻辑分组 (Logical Layer)**。方便人类理解的分类标签（如“音频层”、“业务层”）。
*   ➡️ **实线箭头**: **数据流或控制流**。表示数据从一个模块流向另一个模块，或一个模块控制另一个模块。

## 4. 层级划分 (Layer Architecture)
我们将系统切分为三层：
1.  **System Layer (顶层/紫色)**: 负责基础设施，如网络连接、定时器、系统事件。
2.  **Audio & AI Layer (中层/红黄色)**: 负责核心计算，如音频采集、编码、VAD 检测、AI 推理。这是系统**算力消耗的重灾区**。
3.  **App Logic Layer (底层/绿色)**: 负责业务逻辑，如状态机管理、UI 绘制、用户交互。

## 5. 通信与同步机制 (IPC Objects)
图中未直接画出连线，但在逻辑上至关重要的“隐形血管”：

*   📥 **Audio Queue (音频队列)**
    *   **图形**: 虚线边框的浅蓝色块 `[Audio Queue]`
    *   **含义**: **数据缓冲区 (FIFO)**。
    *   **作用**: 解耦。`AudioInput` 采集得快，`AudioDet` 处理得慢，中间加个队列，就像“蓄水池”，保证水流平稳，不会因为瞬时高负载导致数据丢失（爆音）。
*   🚩 **Event Group (事件组)**
    *   **图形**: 虚线边框的浅蓝色块 `[Event Group]`
    *   **含义**: **信号旗 (Flags)**。
    *   **作用**: 同步。例如，当 `Wifi` 连上了，它举起一面旗子（Set Bit）；`Mqtt` 任务一直在盯着这面旗子（Wait Bit），看到旗子举起来了，它才开始连接服务器。这比 `Retry` 轮询高效得多。

## 6. 故障排查：如何抓“堵点”？ (Troubleshooting)
拿到一张新的拓扑图快照时，请按以下步骤自检：

1.  **找红色 (Find the Hotspots)**:
    *   谁最红？如果是 `audio_input` (43%)，结合 OPUS 编码特性，这是正常的。
    *   如果是 `main` 或 `mqtt` 变红，说明业务逻辑里有死循环或不合理的耗时操作。
2.  **看 Prio 倒挂 (Priority Inversion)**:
    *   有没有 **低优先级的耗时任务** 抢占了 **高优先级任务** 的 CPU？
    *   *案例*: 优化前，`imu_ai_task` (Prio:5) 长期占用 33%。如果它的优先级被错误地设为 >8，就会导致 `audio_input` (Prio:8) 无法及时运行，产生音频爆音。
    *   **原则**: 耗时任务（如 AI 推理）必须比实时任务（如 音频/电机）优先级低，或者主动让出 CPU (`vTaskDelay`)。

这张图不仅是文档，更是**定责工具**：系统卡顿是因为**算力不够**（全红），还是**调度不公**（优先级设置错误）。
